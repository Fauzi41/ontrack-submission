04 / SOLUTION ARCHITECTURE

Arsitektur Full-Stack Modular, Lokal & Zero-Native-Friction

TypeScript • React • Express • node:sqlite

Frontend (React 19 + Vite + Tailwind)

  • PortfolioView.tsx: Executive KPIs, filter perhatian, kartu perbandingan Reported vs Operational.
  • ProjectDetailView.tsx: 3-Layer Truth Cards, Attention Signals dengan provenance tags, panel Unknowns, Unified Timeline + Raw JSON inspector.
  • DeadlineBreakdown.tsx: Visualisasi garis waktu + tabel audit perhitungan 7 langkah.
  • FollowUpPanel.tsx & RefreshModal.tsx: Siklus tindak lanjut, verifikasi bukti, & live ingest console.

Backend API & Intelligence Engine

  • parsers.ts: Validasi ketat CSV/JSON; karantina baris rusak tanpa memaksa angka jadi 0 (P6).
  • deadlineEngine.ts: Kalkulasi durasi, run-rate, required pace, acceleration factor, slip, & capacity ceiling.
  • intelligenceEngine.ts: Mesin aturan deterministik R1–R6 bebas hardcoding project_id.
  • app.ts: 10 REST endpoints tervalidasi Zod (/portfolio, /projects/:id, /followups, /verify, /refresh, /ingest).

Persistence (SQLite WAL — node:sqlite)

  • source_masters, source_updates, source_production (dengan payload_hash untuk deteksi duplikat/konflik).
  • follow_ups: menyimpan action_status terpisah dari verification_status & resolved_at.
  • follow_up_history: audit trail permanen tiap transisi status & verifikasi bukti.
  • ingestion_runs: log transparan tiap startup, disk refresh, dan live ingest beserta warning.

Mengapa Pilihan Stack Ini Optimal?

1. Zero Build Friction: Menggunakan node:sqlite bawaan Node 22.5+/24 sehingga tidak perlu kompilasi native C++ (node-gyp) di Windows/Mac/Linux.
2. Clean Testability: createApp({ db, dataDir }) menerima SQLite :memory: maupun file sementara untuk uji isolasi & persistensi restart.
3. Change Readiness: Sumber data diproses ulang lewat POST /api/refresh atau POST /api/ingest langsung dari UI saat sesi Q&A.

05 / EXPLAINABLE ATTENTION & DEADLINE MATH

Aturan Generik R1–R6 & Metodologi Perhitungan Deadline

100% Deterministic & Auditable

Mesin Aturan Generik (Nol Branching project_id)

RuleLogika Deteksi GenerikLevel
R1|reported_progress_pct - (actual/target×100)| > 0.5%MED/HIGH
R2Averified + pending ≈ reported_actual → Workflow-State Gap (bukan error)MEDIUM
R2BSelisih reported_actual vs log operasional tanpa pending recordHIGH
R2Cdeveloped_endpoints > production_tested_endpoints (DoD Gap)CRITICAL
R3Required Pace > Max Capacity / Accel ≥ 1.75x / Slip ≥ 7dCRIT/HIGH
R4Scanner OUT_OF_SERVICE/LIMITED, Env NOT_CONFIGURED, Skipped > 0, Hold/ReworkCRIT/HIGH
R5Proyek aktif tanpa update & log operasional ≥ 72 jam → Blind SpotHIGH UNC.

7 Langkah Perhitungan Deadline (deadlineEngine.ts)

  1. Total Duration: Deadline - Start Date (selisih hari kalender UTC).
  2. Elapsed & Remaining: Elapsed = As-Of - Start | Remaining = Deadline - As-Of.
  3. Audit Persentase: Computed % = (Reported Actual / Target) × 100%.
  4. Historical Run-Rate: Actual / Elapsed Days (untuk data usang >72j, pembagi berhenti di tanggal snapshot terakhir agar tidak mengasumsikan output 0).
  5. Required Daily Pace: (Target - Actual) / Remaining Days.
  6. Acceleration & Projected Slip: Accel = Required / Historical | Finish = As-Of + ceil(Remaining / Historical).
  7. Capacity Ceiling Check: Bila kapasitas harian disebut di update (mis. 4.500 pages/hari), uji Remaining / Max Capacity untuk membuktikan kelayakan fisik.

Mekanisme Pemisahan Status di Backend & UI

  • Dua State Independen: action_status (OPEN, IN_PROGRESS, RESOLVED, CANCELLED) dipisahkan secara skema dari verification_status (NOT_APPLICABLE, AWAITING_EVIDENCE, VERIFIED_BY_EVIDENCE).
  • Guard Otomatis saat RESOLVED: Sistem langsung memunculkan banner amber "Action Closed ≠ Operational Issue Resolved" dan tidak menghapus sinyal perhatian proyek.
  • Validasi Timestamp Ketat (POST /api/followups/:id/verify): Menolak (400 Bad Request) bila bukti yang ditautkan lebih lama dari resolved_at atau milik proyek lain.

Contoh Live Flow (Teruji di Automated Test & UI)

  • Step 1: Buat follow-up untuk PRJ-005 (Owner: Kevin, linked: R4B_ENVIRONMENT_NOT_READY, ref: API-EPS-002).

10 / SCALE RISKS & NEXT STEPS

Evolusi Menuju Produk Nyata OnTrackProject.ai

Roadmap & Scale Readiness

Apa yang Pertama Kali Bottleneck di 500 Proyek + Daily Updates?

  • N+1 On-the-Fly Recomputation: Memuat ratusan ribu baris update & snapshot di setiap request /api/portfolio akan memicu lonjakan latensi.
  • SQLite Single-Writer & Full-File Reload: Konkurensi ingest dari banyak sistem operasional akan antre di write-lock SQLite.
  • Cumulative Average Velocity: Pada proyek multi-bulan, rata-rata sejak hari pertama terlambat mendeteksi penurunan performa mendadak di minggu terakhir.
  • Free-Text Regex Limits: Variasi bahasa pesan lapangan di 500 proyek membutuhkan taksonomi blocker terstruktur.

Prioritas Pengembangan Berikutnya (2 Hari → Production)

  • Fase 1 (Scale & Accuracy): Materialized project_intelligence_snapshots per ingestion event + Rolling 7-Day Velocity & grafik burn-up harian.
  • Fase 2 (Configurable Control): Ambang batas aturan (staleness, pace ratio, math tolerance) dapat dikonfigurasi per project_type + auto-reconciliation follow-up saat bukti baru menghilangkan sinyal.
  • Fase 3 (Enterprise Control Layer): Migrasi ke PostgreSQL, konektor webhook/API otomatis dari DMS/ERP/Scanner, autentikasi SSO + RBAC (separation of duties pada verifikasi penutupan), serta E2E Playwright tests.
